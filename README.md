# Beehive Monitoring System

A low-power ESP32 data logger for remote honeybee hive monitoring. The node wakes on a timer, samples its sensors, writes everything to an SD card, periodically emails the accumulated data over WiFi, and sleeps through the night. Because it spends almost all of its time in deep sleep, the application runs once per wake rather than continuously every boot is a fresh start, not a continuation.

Sensing is split across four devices. An SHT45 measures in-hive temperature and humidity, the parameters a healthy colony thermoregulates most tightly. A load cell measures total hive weight. An ICS43434 I2S MEMS microphone records the colony's acoustic signature. A MAX17043 fuel gauge reports battery state of charge and terminal voltage, serving both as node health telemetry and as a safety interlock. Timestamps and scheduling come from a battery-backed DS3231 real-time clock.

A boot begins by powering the peripheral rail, then initialising the real-time clock and running a sanity check on it as an extra safeguard before any logging happens. The check catches a clock that has lost its time and would otherwise stamp records with a meaningless date; if it fails, the node sleeps and retries on the next wake instead of writing anything. The fuel gauge is read next; a missing gauge is tolerated and simply reports unavailable, but a pack voltage at or below 3.600 V triggers a low-battery email and permanent sleep rather than discharging the cell into damage. The SD card is mounted third, and a mount failure also routes to permanent sleep, but only after the card has been powered down cleanly.

Power management is dominated by the SD card, which draws current continuously even when the bus is idle and will flatten a battery far faster than the sleeping microcontroller ever would. It is therefore switched off entirely between cycles using an N-channel MOSFET as a low-side switch on its ground path. The gate is driven high at boot to power the card for the awake period. At the end of the cycle the shutdown is deliberately ordered: the card is unmounted and flushed first, then the rail is cut, then chip select is pulled low so the card cannot be back-powered parasitically through its I/O pins. Ordering matters, because cutting power mid-write corrupts the filesystem and in the worst case destroys the card's controller. The same sequence runs on the failure path, so a card that fails to mount is never left powered.

Scheduling works on two independent layers. The first is a day/night window, derived from a compact table of sunrise and sunset times for the first of each month and linearly interpolated by day-of-month to approximate the daily solar window without any astronomical maths at runtime. If the current time falls outside that window the node computes the seconds remaining until sunrise, sends a notification, sleeps through, and on waking sends a good-morning email before resuming — bees are not active at night, so there is nothing worth spending battery on.

The second layer governs how often individual measurements run. Each is wrapped in a small task behind a common interface with two responsibilities: deciding whether it is due on the current boot, and doing the work. Due-ness is a simple modulo test against a persistent boot counter, which therefore acts as a modular clock and removes any need for separate timers. An expensive audio recording or WiFi upload can run once every several dozen boots while a temperature reading runs on nearly all of them. Logging frequency is changed entirely in the config file, where a base sleep duration sets the fundamental tick and each task interval sets how many ticks pass between runs; no task logic changes, and adding a new sensor means adding a task and one entry to the task list.

The tasks reflect this structure. Audio brings the microphone up and tears it down around each recording so it draws nothing in between, writing to both the permanent archive and the transmit folder only on boots where an upload is also due. The load cell initialises, reads, writes, and immediately sleeps its amplifier. Temperature and humidity readings are validated against a sentinel value and the write is skipped rather than logging a failed sample. The upload task associates with a bounded 25-second timeout, resynchronises the clock, sends the accumulated data with the current battery state attached, and clears the transmit folder only if the send succeeded a failure keeps the files for the next cycle, so an unreliable network never costs data, and the radio is fully shut down afterwards.

Two pieces of state have to survive across boots, and both use the same two-tier approach. The boot counter and the load cell tare offset are held in the microcontroller's RTC memory, which survives deep sleep, and mirrored to the SD card, which survives a full power loss. On a cold start the SD copies are read back and sanity-checked, so a missing or implausible value resets cleanly instead of corrupting the schedule or the weight readings. Boot zero is handled as a special case: only the load cell runs, purely to establish a tare, and its reading is deliberately discarded so that the first untared measurement never enters the dataset.

Failure handling throughout distinguishes between problems that cost a capability and problems that would corrupt the dataset. A missing fuel gauge, an invalid sensor read or a failed email each disable one function and let the rest of the cycle complete. An invalid clock, a failed SD mount, or a critical battery instead route the node to permanent sleep, because logging misdated or unwritable data or damaging the cell is worse than not logging at all.

The system has been deployed in the field and validated under continuous operation. In that deployment the load cell was sampled once a minute, temperature and humidity every fifteen minutes, a ten-second audio clip was recorded every thirty seconds, and the accumulated data was uploaded over WiFi every three hours. Running at those rates, the node operated for a full day on a single 2000 mAh cell a demanding duty cycle for that capacity, given that audio capture and radio transmission are by far the most expensive operations in the system, and one that confirms the value of aggressively power gating the SD card and shutting down each peripheral immediately after use.
